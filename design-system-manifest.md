# Design system manifest

This is the design law for Manti UI. Fabrika's `build-ui` and `review-ui`
stages judge every rendered change against it. It restates the visual rules in
`CLAUDE.md` / `AGENTS.md` (rules 2 to 6) as one reference; when the two
disagree, `CLAUDE.md` wins and this file is out of date.

Manti UI is a substrate, not a finished opinionated system: consumers build
their own look on top of it. So defaults live in CSS and tokens, never in JSX,
and every visual decision must be something a consumer can redefine in a
stylesheet without forking a component.

## Identity

- **Sleek, monochrome, cool.** Neutral surfaces sit near hue 280 with very low
  chroma. Dark is the hero theme: a near-black cool surface. Light is a soft
  daylight that is never pure white.
- **Hierarchy comes from surface contrast, borders, spacing and layering.**
  Never from shadows, glows on controls, or gradients.
- **Color carries meaning, not decoration.** Neutral chrome is the default;
  hue appears only through the semantic `variant` vocabulary (`primary`,
  `secondary`, `tertiary`, `danger`, `success`, `warning`, `info`).

## Tokens are the only source of visual values

- Every color, spacing, radius, typography, motion, elevation and z-index value
  comes from `@manti-ui/tokens`, consumed as `--manti-*` and `--variant-*` CSS
  custom properties. No hex or `oklch()` literals, no raw `px` sizes, no magic
  numbers in component CSS.
- Three tiers: primitive ramps, then semantic roles and the `--variant-*`
  vocabulary, then component tokens (`--manti-{component}-{property}`). Component
  CSS consumes the semantic or component tier, never a primitive ramp stop.
- An independent structural value a component needs (radius, padding, sizing,
  gap, typography) is exposed as a component token registered in the
  `componentTokens` map. Only derived `calc()` values stay private as `--_*`.
- A missing value is added to `@manti-ui/tokens` first, then consumed.
- The `@tokens:generated` region of `packages/styles/src/tokens.css` is
  generated by `pnpm gen:tokens` and never hand-edited.

## Color roles and interaction

- Ramps run `1` to `12`, and the roles map onto them centrally in
  `packages/styles/src/tokens.css`, theme-aware through `light-dark()`:
  `1`-`2` canvas and subtle surfaces; `3` rest, `4` hover and keyboard
  highlight, `5` pressed, selected, checked; `6` quiet chrome, `7` interactive
  borders, `8` focus rings and strong chrome; `9` solid fill, `10` solid hover;
  `11` supporting text, `12` high-contrast text.
- Filled and selected surfaces step rest, hover, active as `3`, `4`, `5`
  through the variant roles (`--variant-soft-bg`, `--variant-soft-bg-hover`,
  `--variant-soft-bg-active`). Solid controls step `9` to `10`
  (`--variant-solid`, `--variant-solid-hover`). Strength grows in the direction
  that gains contrast in each theme.
- **Input-like controls** (Input, Textarea, Select, Combobox, NumberInput,
  PinInput, TagsInput, Editable, DatePicker, TimePicker, ColorPicker,
  Clipboard) rest on `--manti-border`, strengthen to the neutral
  `--manti-border-strong` on hover, and take `--variant-ring` only while
  active, focused or open. A variant color never paints their rest or hover
  border.
- **Connected popups** (Select, Combobox) are one surface with one outline:
  the trigger keeps `--manti-border` while open, and only the seam edge shared
  with the popup is zeroed and tinted to the panel, chosen by `data-side`.
  Never zero a border width unconditionally on open.
- Text meets the contrast gate in both themes:
  `pnpm --filter @manti-ui/styles check:contrast`.

## Surfaces and material

- Controls are flat and opaque: `--manti-surface` with `--manti-border`, or
  `--manti-fill` under `data-appearance="fill"`. Soft treatments merge the
  border into the fill so the 1px footprint stays without a contrasting edge.
- Floating and overlay chrome (card, tooltip, `.manti-panel`, menus, popovers,
  the connected Select/Combobox popup, toasts) may use the panel recipe:
  a translucent `color-mix()` fill, the light `--manti-panel-blur`, the
  `--manti-panel-border` hairline and the `--manti-panel-highlight` rim.
- Any `backdrop-filter` pairs `-webkit-backdrop-filter` and an `@supports not`
  opaque fallback in the same layer, so every reader sees the same design.
- Small marks stay crisp and opaque: solid button, badge, alert and toggle-on
  fills, checkbox and radio boxes, switch track and thumb.

## Size

- `sm | md | lg` is one shared rhythm, resolved from the `--manti-size-*`
  channel in `packages/styles/src/size.css`. Component tokens default to it.
- A popup is portalled out of its control, so the adapter re-stamps
  `data-size` on the positioner: a `sm` Select opens a `sm` listbox. A sized
  control never opens a fixed-size surface.
- Components that spend `data-size` on something else (Dialog width, Avatar
  diameter, DataTable density) never open the channel.

## Typography

- The type scale is the token set `--manti-text-*`, `--manti-weight-*`,
  `--manti-leading-*`, `--manti-tracking-*`, rendered by `Text` and `Heading`.
- In stories, demos and docs, copy renders through `Text` and `Heading` (the
  `as` prop covers spans, labels and other elements), never a raw `<h1>`-`<h6>`
  or `<p>`.
- Inside an adapter, an anatomy part that carries the machine's
  `data-scope`/`data-part` (such as Dialog's title) stays a native element and
  composes its look in CSS from the typography tokens only.

## Focus and accessibility

- Every interactive part has a visible focus state, drawn with
  `--manti-focus-ring`, `--manti-focus-ring-width` and
  `--manti-focus-ring-offset` as an outline. Focus emphasis is neutral.
- Public components ship keyboard support and meaningful screen-reader
  semantics. Decorative parts are `aria-hidden`; meaningful content never is.
- Motion uses the `--manti-duration-*` and `--manti-ease-*` tokens.

## Examples and stories

- Stories and demos are built from real Manti components (Button, Card, Badge
  and so on), never raw HTML stand-ins.
- Every public component has stories for its variants, its disabled and error
  states, and its meaningful interactions.

## Prohibitions

These are blocking. A rendered change that breaks one fails review.

1. **No `box-shadow`**, anywhere: components, utilities, docs surfaces,
   examples, motion states, focus treatments. No shadow tokens and no
   shadow-based elevation. An outline is allowed only for a real boundary, a
   focus state or a functional mask.
2. **No gradients** on fills, text (`background-clip`), edges, indicators,
   buttons or component accents. The only gradients are the three faint
   `radial-gradient` ambient glows in `packages/styles/src/base.css`.
3. **No raw visual values** in component CSS: no hex or color literals, no raw
   `px` spacing, radius or font values, no bare z-index or duration numbers.
   Use a token, or add one.
4. **No primitive ramp stops in component CSS.** Consume semantic roles or the
   `--variant-*` vocabulary.
5. **No variant color on an input-like control's rest or hover border.**
6. **No raw font sizes, weights, line heights or letter spacings** in component
   CSS, and no raw `<h1>`-`<h6>` or `<p>` in stories, demos or docs.
7. **No fixed-size popup under a sized control**, and no size channel opened by
   a component that spends `data-size` on something else.
8. **No `backdrop-filter` without its `-webkit-` pair and opaque fallback.**
9. **No hidden meaning**: content a user needs is never `aria-hidden`, and
   color or an icon is never the only cue.
